# Управление пользователями

Веб-приложение: список пользователей, поиск по имени, добавление и удаление. Node.js без фреймворков + TypeScript.

## Запуск

Требуется Node.js 22 или новее.

```bash
cd submissions/PetrKopyev
npm ci
npm start      # сборка и запуск: http://127.0.0.1:3000
npm test       # серверные тесты API и валидации + тесты клиентского API-модуля и загрузчика списка (node:test, без браузера)
```

Сервер слушает `127.0.0.1`; порт и адрес меняются переменными окружения: `PORT=4000 HOST=0.0.0.0 npm start`.

## Технологии

- **`node:http`**, без фреймворков и runtime-зависимостей: для пяти маршрутов фреймворк не нужен, меньше кода и поверхности для ошибок.
- **TypeScript через `tsc`**: dev-зависимости только `typescript` и `@types/node`, версии зафиксированы.
- **Один сервер для API и статики**: нет CORS; статика отдаётся только по белому списку путей (обход каталогов невозможен).
- **`node:test`**: тесты без внешнего раннера.
- **Клиент**: ES-модули без сборщика; DOM строится через `textContent` (без `innerHTML`), поиск с debounce 300 мс и `AbortController` против гонок ответов, подтверждение удаления в нативном `<dialog>`.

## Что бы улучшил

- E2E-тесты интерфейса в браузере: сейчас тестируются сервер, API-модуль и загрузчик списка клиента, а не сама страница.
- Постоянное хранилище: данные лежат в памяти (`store.ts`) и теряются при перезапуске.
- Пагинация: `GET /api/users` отдаёт весь список целиком.
- Ограничение частоты запросов и числа записей: память под пользователей ничем не ограничена.
- Структурированное логирование: сейчас в консоль пишутся только запуск и необработанные ошибки.

## Структура

- `src/server` — HTTP-сервер, маршруты, валидация, хранилище в памяти, тесты.
- `src/client` — код страницы (`app.ts`), запросы к API (`api.ts`), загрузка списка без гонок (`loader.ts`), уведомления (`toast.ts`); тесты для `api.ts` и `loader.ts`.
- `src/shared` — общие типы `User` и `NewUser`.
- `public` — `index.html` и `style.css`.

## API

| Метод | Путь | Успех | Ошибки |
| --- | --- | --- | --- |
| GET | `/api/users`, `/api/users?name=...` | `200`, массив пользователей | — |
| POST | `/api/users` | `201`, созданный пользователь | `400 VALIDATION_ERROR` / `INVALID_JSON`, `409 EMAIL_TAKEN`, `413 PAYLOAD_TOO_LARGE`, `415 UNSUPPORTED_MEDIA_TYPE` |
| DELETE | `/api/users/{id}` | `204`, пустое тело | `400 INVALID_ID`, `404 NOT_FOUND` |

Поиск `name` — по подстроке без учёта регистра, пробелы по краям игнорируются. В хранилище 10 начальных пользователей. Неподдерживаемый метод — `405 METHOD_NOT_ALLOWED` с `Allow`, неизвестный путь `/api/*` — `404 NOT_FOUND`, внутренняя ошибка — `500 INTERNAL`.

Формат ошибки (`fields` есть только у ошибок полей и `409`):

```json
{ "error": { "code": "VALIDATION_ERROR", "message": "Проверьте введённые данные", "fields": { "email": "Некорректный email" } } }
```

Валидация `POST /api/users`:

- `Content-Type: application/json`, тело — JSON-объект до 10 КБ (больше — `413`).
- `name`: строка после `trim` с хотя бы одной буквой или цифрой, до 100 символов, без управляющих символов.
- `email`: строка после `trim`, приводится к нижнему регистру, до 254 символов, должна быть корректным адресом.
- Email уникален без учёта регистра, иначе `409 EMAIL_TAKEN`.
- `id` в `DELETE` — положительное целое, иначе `400 INVALID_ID`; id не переиспользуются после удаления.

Примеры:

```bash
curl -i -X POST http://127.0.0.1:3000/api/users \
  -H 'Content-Type: application/json' \
  -d '{"name":"Ivan Petrov","email":"ivan@example.com"}'
# HTTP/1.1 201 Created
# {"id":11,"name":"Ivan Petrov","email":"ivan@example.com"}

curl -i -X POST http://127.0.0.1:3000/api/users \
  -H 'Content-Type: application/json' \
  -d '{"name":"","email":"bad"}'
# HTTP/1.1 400 Bad Request
# {"error":{"code":"VALIDATION_ERROR","message":"Проверьте введённые данные","fields":{"name":"Укажите имя","email":"Некорректный email"}}}
```
