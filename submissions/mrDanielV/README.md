# Тестовое задание: Fullstack-разработчик

Решение тестового задания: просмотр, добавление и удаление пользователей.

## Стек

- **Backend:** Node.js (встроенный модуль `http`), TypeScript.
- **Frontend:** HTML5, CSS3, TypeScript (компилируется в один JS-файл, без фреймворков).
- **Зависимости:** только `typescript` и `@types/node` (devDependencies, для компиляции). Runtime-зависимостей нет.
- **Данные:** в памяти процесса (in-memory), сброс при перезапуске сервера.

## Запуск

Требуется Node.js v18+ (рекомендуется v20 или v24).

```bash
# 1. Установить зависимости (только компилятор TS)
npm install

# 2. Собрать проект (сервер + клиент)
npm run build

# 3. Запустить сервер
npm start
```

    └── src/

Чуть подробнее о раскладке:

- `server/src/index.ts` — точка входа сервера: `createServer`, функция `handleApi` для маршрутов `/api/*` и раздача статики из `client/`.
- `server/src/users.ts` — in-memory массив и функции доступа к нему (`getAll`, `create`, `removeById`, `findByEmail`). Массив наружу не экспортируется.
- `server/src/validation.ts` — серверная валидация `POST /api/users` (порядок проверок и нормализация полей).
- `server/src/http-utils.ts` — низкоуровневые помощники для HTTP: `sendJson`, `sendNoContent`, `readBody`.
- `client/src/app.ts` — единственный клиентский TS-файл: загрузка, рендер, поиск с debounce, создание и удаление. Компилируется в `client/dist/app.js` и подключается как обычный `<script>`.

## API

| Метод | Путь | Описание | Успех | Ошибки |
|-------|------|----------|-------|--------|
| `GET` | `/api/users` | Список пользователей | `200` + `User[]` | `500` |
| `GET` | `/api/users?search=...` | Поиск по имени (без учёта регистра) | `200` + `User[]` | `500` |
| `POST` | `/api/users` | Создать пользователя | `201` + `User` | `400` (валидация), `409` (email занят), `415` (не JSON) |
| `DELETE` | `/api/users/:id` | Удалить пользователя | `204` (без тела) | `400` (некорректный id), `404` (не найден) |

Формат ошибки: `{ "error": "текст сообщения" }`.

Модель `User`:

```json
{ "id": 1, "name": "Alex", "email": "alex@example.com" }
```

## Выбранные технологии и почему

- **TypeScript** — в вакансии указан как основной язык; строгая типизация (`strict: true`) помогает ловить ошибки на этапе компиляции. Для клиента используется один TS-файл без модулей — это позволяет обойтись без сборщика (Webpack/Vite), которые запрещены условиями задания.
- **Встроенный `node:http`** — по условиям нельзя использовать Express и другие фреймворки. Роутинг реализован вручную через `req.method` + `URL`.
- **`@types/node`** — только декларации типов для компилятора, в рантайм не попадает. Без него `tsc` не видит `node:http`, `Buffer`, `process`.
- **In-memory хранилище** — по условиям БД не требуется; данные сбрасываются при перезапуске.
- **Debounce + AbortController на поиске** — снижает нагрузку на сервер и защищает от race condition (устаревшие ответы не перезаписывают новые).
- **Делегирование событий для удаления** — один обработчик на `#users-body` вместо N обработчиков на динамически создаваемых кнопках.

## Что бы улучшил при наличии дополнительного времени

- **Тесты.** Добавил бы юнит-тесты на `validation.ts` и `users.ts` (встроенный `node:test`, без зависимостей) и e2e-тест API через `fetch`.
- **Оптимистичный UI.** Сейчас после создания/удаления список перезагружается целиком. Можно обновлять локально, а при ошибке — откатывать.
- **Пагинация.** При большом количестве пользователей список стоит разбивать на страницы (`?page=&limit=`).
- **Более строгая валидация email.** Текущая регулярка простая (соответствует ТЗ «простая, но рабочая»); для продакшена — проверка через библиотеку или отправка confirmation-письма.
- **Улучшение UX.** Подтверждение удаления (`confirm()` или модалка), тосты вместо инлайн-ошибок, скелетоны вместо текста «Загрузка...».
- **Обработка сигналов.** Graceful shutdown по `SIGTERM`/`SIGINT` — сейчас сервер просто завершается.
- **Типизация ответов API.** Общий тип `ApiError = { error: string }` и хелпер для парсинга ответа на клиенте, чтобы не дублировать `try/catch` в каждом запросе.
