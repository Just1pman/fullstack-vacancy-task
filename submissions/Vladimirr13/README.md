# Справочник пользователей

Решение тестового задания: просмотр, поиск по имени, добавление и удаление пользователей.

## Запуск

Нужен Node.js **22 или новее** и npm. Runtime-зависимостей нет. Для компиляции используются только devDependencies: `typescript` и `@types/node`.

Из корня репозитория:

```sh
cd submissions/Vladimirr13
npm ci
npm start
```

`npm start` сначала компилирует TypeScript и копирует HTML/CSS в `dist/`, затем запускает сервер. Откройте **http://127.0.0.1:3000**. Для остановки нажмите Ctrl+C.

Режим разработки с пересборкой и перезапуском при изменениях в `server/`, `public/`, `contracts/` или `tsconfig.json` (наблюдение за путями поддерживается Node.js на macOS и Windows):

```sh
npm run dev
```

После изменения frontend обновите страницу браузера. На Linux можно повторять `npm start` после изменений. Другой порт можно задать переменной окружения, например в macOS/Linux: `PORT=3001 npm start`.

## Проверка

```sh
npm run typecheck  # проверка типов без генерации файлов
npm test           # сборка и запуск тестов
```

Отдельная сборка: `npm run build`. Скомпилированные файлы находятся в `dist/` и исключены из Git вместе с `node_modules/`. Исходники приложения — TypeScript; тесты на JavaScript запускаются против собранных модулей.

Интеграционные тесты запускают настоящий HTTP-сервер на свободном локальном порту. Каждый тест получает отдельное хранилище. Проверяются поиск, создание, удаление, уникальность ID, серверная валидация, ошибки JSON, HTTP-статусы, ограничение тела запроса и доступность только разрешённых статических файлов.

Отдельно проверяются API-клиент и контроллер интерфейса: отмена обновления после удаления, устаревшие ответы поиска, повторные отправки, ошибки создания и обновления списка. Контроллер тестируется с управляемыми ответами API и подменой представления без браузера; эти проверки не заменяют визуальную проверку страницы.

Ручная проверка в браузере:

1. Открыть страницу: отображаются 10 пользователей.
2. Ввести `aNN`: остаётся Anna Volkova. Очистить поиск: отображается весь список.
3. Ввести отсутствующее имя: появляется сообщение об отсутствии совпадений.
4. Добавить пользователя: форма очищается, список обновляется. При активном поиске сохраняется фильтр.
5. Отправить пустые поля, имя из пробелов или некорректный email: ошибочные поля подсвечиваются и появляется одно короткое сообщение под кнопкой, фокус переходит на первое поле с ошибкой, запрос не отправляется. Исправить данные и повторить отправку. Сервер отдельно проверяется негативными API-тестами.
6. Удалить пользователя: запись исчезает после успешного запроса.
7. Остановить сервер и выполнить поиск или отправку формы: появляется понятная ошибка. Запустить сервер снова и нажать «Повторить загрузку».
8. Проверить страницу на узком экране и навигацию клавишей Tab.

## Технологии и структура

TypeScript со строгой проверкой (`strict: true`, `noUncheckedIndexedAccess`, `noImplicitReturns`), ES-модули, Node.js (`node:http`, `node:fs`), HTML, CSS и встроенные API браузера. Для тестов используются `node:test` и `node:assert`. Один сервер обслуживает страницу и API с одного origin, поэтому отдельные frontend-сервер и настройка CORS не нужны.

```text
server/index.ts       запуск HTTP-сервера
server/app.ts         маршрутизация API, ошибки и статические файлы
server/http.ts        чтение JSON, ответы и проверка HTTP-методов
server/config.ts      настройки HTTP-сервера и разрешённая статика
server/users.ts       начальные данные и операции с массивом
server/validation.ts серверная валидация и ошибки API
public/index.html    разметка страницы
public/styles.css    адаптивные стили
public/api.ts        запросы к API
public/app.ts        создание и связывание модулей приложения
public/users-controller.ts состояние, поиск, создание и удаление
public/view.ts       DOM, отображение, события и фокус
public/notifications.ts уведомления и таймер скрытия
contracts/user.ts    модель пользователя, контракт API и проверки ответов
public/types.ts      интерфейсы контроллера, представления и уведомлений
contracts/user-validation.ts общие правила проверки полей
tsconfig.json       строгая проверка типов и настройка сборки
scripts/            копирование статики и запуск разработки
tests/api.test.js    интеграционные тесты API
tests/api-client.test.js проверки обработки ответов API-клиентом
tests/ui-state.test.js регрессионные проверки состояния интерфейса
```

Frontend получает и изменяет данные только через API. Поиск выполняется на сервере с задержкой ввода 250 мс; отмена запросов и счётчик версий защищают от устаревших ответов. После создания или удаления список запрашивается заново с текущим фильтром. Ошибка обновления списка не выдаётся за ошибку уже выполненной операции. Повторная отправка формы и повторное удаление одной записи блокируются на время запроса. Пользовательский текст выводится через `textContent`.

Общие типы `User`, `UserInput` и ошибки полей используются сервером и клиентом. Входящий JSON на сервере имеет тип `unknown` и проходит runtime-валидацию: TypeScript её не заменяет. Интерфейсы API, представления и действий проверяют согласованность модулей при сборке. API-клиент читает JSON как `unknown` и проверяет структуру пользователей и ошибок перед использованием.

Контроллер хранит состояние в замыкании и обращается к представлению через небольшие методы. Представление отвечает за DOM, а уведомления имеют отдельный модуль. При начале удаления обновляется только кнопка нужной строки; при перерисовке предусмотрено восстановление фокуса. Браузерные всплывающие сообщения отключены через `novalidate`. Перед отправкой контроллер проверяет поля по общим с сервером правилам, подсвечивает ошибочные поля, показывает одну короткую строку под кнопкой и переводит фокус на первое ошибочное поле. Сервер независимо выполняет ту же проверку для каждого POST-запроса. Ошибки полей очищаются по мере редактирования. Под общим сообщением зарезервирована одна строка; ошибки запросов создания без привязки к полям показываются отдельным уведомлением и не меняют высоту формы.

## API

| Метод и путь | Результат |
| --- | --- |
| `GET /api/users` | `200`, массив пользователей |
| `GET /api/users?search=ann` | `200`, поиск по части имени без учёта регистра |
| `POST /api/users` | `201`, созданный пользователь |
| `DELETE /api/users/:id` | `204`, без тела |

Создание требует `Content-Type: application/json` и тела:

```json
{ "name": "Анна Иванова", "email": "anna@example.com" }
```

Ответ:

```json
{ "id": 11, "name": "Анна Иванова", "email": "anna@example.com" }
```

Правила:

- `name` и `email` — строки; пробелы по краям удаляются сервером.
- Имя: 1–100 символов после удаления пробелов, без управляющих символов.
- Email: до 254 символов, базовая проверка формата `имя@домен.зона` без пробелов. Каждая часть домена между точками содержит 1–63 латинских буквы, цифры или дефисы; дефисы по краям и пустые части запрещены. Международные домены можно указать в ASCII-форме Punycode. Проверка существования почтового ящика не выполняется.
- ID — положительное безопасное целое число. Начальный ID вычисляется как максимум ID исходных записей плюс один (для пустого списка — 1). Сервер назначает возрастающий ID и не использует удалённые ID повторно в рамках одного запуска. Переданный клиентом ID и дополнительные поля игнорируются.
- Одинаковые email разрешены: уникальность не требуется заданием.
- Пустой поиск возвращает всех пользователей, отсутствие совпадений — `[]`.
- Размер JSON ограничен 16 КБ.
- Данные хранятся **только в памяти**: при перезапуске восстанавливаются 10 начальных записей.

Ошибки: `400` — некорректные данные/JSON/ID; `404` — отсутствующий пользователь или маршрут; `405` — неподдерживаемый метод (с заголовком `Allow`); `413` — слишком большое тело; `415` — неподдерживаемый Content-Type; `500` — неожиданная ошибка сервера.

```json
{
  "error": {
    "message": "Проверьте данные пользователя.",
    "fields": { "email": "Введите корректный email длиной до 254 символов." }
  }
}
```

`fields` присутствует только для ошибок валидации полей. Подробности внутренних ошибок остаются в консоли сервера.

## Что можно улучшить при дополнительном времени

- Автоматизировать браузерные сценарии, включая задержки и сетевые сбои, если будут разрешены инструменты для E2E-тестов.
- Проверить управление фокусом и озвучивание состояний со скринридером в разных браузерах.
- При увеличении числа записей согласовать пагинацию API.

База данных, авторизация, редактирование, Docker и деплой не добавлены согласно объёму задания.
