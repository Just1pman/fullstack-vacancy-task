# user-management

Веб-приложение для просмотра, поиска, добавления и удаления пользователей. Реализовано на TypeScript без сторонних библиотек и фреймворков, необходимых во время выполнения приложения.

## Установка и запуск

Для запуска необходимы Node.js и npm.

Работоспособность приложения проверена на Node.js 22.12.0 и 26.13.0.

Выполнить из каталога решения:

```bash
npm ci
npm start
```

Frontend и backend будут автоматически собраны, после чего запустится HTTP-сервер.

Приложение доступно по адресу: http://127.0.0.1:3000/.

Данные хранятся в памяти сервера и сбрасываются до начального состояния при его перезапуске.

## Режим разработки

Запуск backend:

```bash
npm run dev:backend
```

Запуск frontend в отдельном терминале:

```bash
npm run dev:frontend
```

Frontend доступен по адресу http://localhost:5173/, backend — http://127.0.0.1:3000/.

Запросы к API проксируются через Vite.

## Используемые технологии

- **TypeScript** — статическая типизация frontend и backend.
- **Node.js** — реализация HTTP-сервера и REST API средствами встроенных модулей.
- **HTML и CSS** — построение и стилизация адаптивного пользовательского интерфейса.
- **DOM API и EventTarget** — взаимодействие с интерфейсом и управление состоянием приложения.
- **Fetch API и AbortController** — выполнение и отмена HTTP-запросов.
- **Vite** — организация среды разработки и сборка frontend.
- **SVG** — отображение иконок с использованием общего спрайта.

## Архитектура и особенности реализации

### Frontend

Клиентская часть разделена на несколько слоёв по зонам ответственности:

- **Models** — типы пользовательских данных, состояния приложения и контрактов API.
- **Service** — взаимодействие с REST API, обработка HTTP-ответов и формирование типизированных ошибок.
- **Store** — управление состоянием списка пользователей, координация загрузки, поиска, создания и удаления пользователей.
- **Views** — работа с DOM, отображение состояния приложения и обработка пользовательских действий.

Store реализован на основе нативного `EventTarget`, что позволяет организовать обновление интерфейса при изменении состояния без сторонних библиотек и собственного механизма подписок.

Представления разделены по функциональной ответственности: поиск пользователей, форма создания пользователя и панель со списком пользователей. Каждое представление содержит собственную разметку, стили и логику взаимодействия с DOM.

Общее состояние списка централизовано в Store, а локальное состояние интерфейса, включая ошибки валидации и состояние отправки формы, управляется соответствующими представлениями.

Стили разделены на общие токены дизайн-системы, переиспользуемые стили элементов интерфейса и стили отдельных представлений. Такой подход обеспечивает визуальную согласованность и позволяет изменять оформление без дублирования общих правил.

### Асинхронные операции и синхронизация данных

При реализации клиентской части особое внимание уделено обработке асинхронных операций и согласованности состояния с сервером.

- Поиск выполняется с использованием debounce. Нормализация поисковой строки позволяет избежать повторных запросов при изменении только регистра или пробелов по краям.
- Неактуальные запросы на получение списка отменяются с помощью `AbortController`.
- Первичная загрузка и фоновое обновление списка разделены, что позволяет сохранять отображаемые данные во время синхронизации.
- Состояния удаления отслеживаются независимо для каждого пользователя, благодаря чему несколько операций удаления могут выполняться параллельно.
- После успешного удаления соответствующая запись сразу исключается из клиентского списка.
- После успешного создания или удаления пользователя список синхронизируется с сервером с учётом актуального поискового запроса.
- Если результат операции создания или удаления невозможно однозначно определить из-за сетевой или серверной ошибки, выполняется повторная синхронизация данных.
- Строки списка не пересоздаются при изменениях состояния, не затрагивающих сам массив пользователей.

Повторное получение списка после изменения данных позволяет сохранить сервер в качестве единственного источника истины и не дублировать на клиенте логику поиска и формирования списка.

### Backend

Серверная часть реализована на основе встроенного модуля `node:http` без использования серверных фреймворков.

Маршрутизация и обработка HTTP-запросов, операции с пользовательскими данными, валидация и конфигурация выделены в отдельные модули. Такое разделение позволяет изменять бизнес-логику независимо от обработки HTTP-запросов.

REST API предоставляет следующие методы:

- `GET /api/users` — получение списка пользователей.
- `GET /api/users?search=...` — поиск пользователей по имени без учёта регистра.
- `POST /api/users` — создание пользователя.
- `DELETE /api/users/:id` — удаление пользователя.

API использует соответствующие HTTP-статусы для успешных операций, ошибок валидации, конфликтов данных и других ошибок обработки запросов.

### Валидация и хранение данных

Валидация входящих данных выполняется на сервере. Ошибки отдельных полей возвращаются клиенту и отображаются непосредственно в форме.

В рамках приложения приняты следующие дополнительные правила:

- Имя может содержать буквы Unicode, диакритические знаки, пробелы, дефисы и апострофы между частями имени.
- Поддерживается ограниченный набор распространённых форматов email. В локальной части допускаются латинские буквы, цифры, подчёркивания и одиночные точки между непустыми частями.
- Пробелы по краям имени и email удаляются, email приводится к нижнему регистру.
- Email пользователя должен быть уникальным без учёта регистра. При нарушении этого условия сервер возвращает `409 Conflict`.
- Идентификаторы пользователей генерируются на сервере.
- Новые пользователи добавляются в начало списка.

### Сборка и запуск

Для организации разработки и сборки клиентской части используется Vite.

Небольшой плагин Vite объединяет HTML-фрагменты отдельных представлений и SVG-спрайт на этапе обработки `index.html`. Это позволяет разделять разметку по функциональным модулям без использования шаблонизаторов и клиентских фреймворков.

При обычном запуске собранный frontend и REST API обслуживаются одним Node.js-сервером. Такой подход упрощает запуск приложения и исключает необходимость отдельного сервера для статических файлов и настройки CORS.
