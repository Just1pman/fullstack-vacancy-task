# Пользователи

[Моё резюме на hh.ru](https://hh.ru/resume/ea8de88eff0cf44cd60039ed1f533971324739)

Для запуска нужны Node.js 22 или новее и npm.

Из корня репозитория перейдите в каталог решения:

```bash
cd submissions/trybachok
```

Установите зависимости для сборки:

```bash
npm ci
```

Создайте локальный файл настроек:

```bash
cp .env.example .env
```

В `.env` задаются адрес прослушивания (`HOST`), порт (`PORT`), каталог статических файлов (`PUBLIC_DIR`) и путь к начальному списку пользователей (`USERS_FILE`).
Если `.env` уже создан, добавьте `USERS_FILE=data/users.json`.
Относительные пути отсчитываются от каталога решения. Переменные окружения имеют приоритет над значениями в файле.

При запуске сервер загружает начальный список пользователей из JSON-файла в память. Для файла достаточно права на чтение. Изменения списка хранятся в памяти и сбрасываются при перезапуске.

Соберите и запустите сервер:

```bash
npm start
```

С настройками из примера откройте приложение на [http://127.0.0.1:3000](http://127.0.0.1:3000).

Сервер написан на TypeScript и использует встроенные модули Node.js. Браузер получает HTML и CSS.

Серверный код находится в `src/server/`, код браузера — в `src/client/`, общие типы и правила валидации — в `src/shared/`. Сборка браузера публикуется из `dist/browser/` по адресу `/assets/`.

[Контракт REST API](openapi.yaml) описывает операции с пользователями, серверную валидацию и ответы на ошибки.

## Тесты

```bash
npm test
```

Команда собирает TypeScript и запускает тесты из каталога `tests/` через встроенный `node:test`.

## Что бы я улучшила при наличии дополнительного времени

- Для проверки качества кода подключила бы ESLint с правилами для TypeScript. В первую очередь проверяла бы обработку промисов и небезопасные обращения к полям ответов API. Объединила бы запуск линтера, проверку типов и тесты в одну команду для проверки изменений перед коммитом.
- Усилила бы общий валидатор имени, чтобы он отклонял значения, состоящие только из пробелов и невидимых символов, например пробелов нулевой ширины. Добавила бы граничные тесты для email: часть до `@` длиной 64 символа должна проходить проверку, а длиной 65 — отклоняться с понятной подсказкой.
- Добавила бы браузерные тесты на создание пользователя и обновление списка. Проверила бы, что после сбоя поиска прежние результаты исчезают, кнопку повтора можно нажать с клавиатуры, а после удаления записи в другой вкладке список обновляется.
- Добавила бы редактирование имени и email, чтобы опечатку можно было исправить с сохранением идентификатора пользователя. Форма отправляла бы изменённые поля через `PATCH /api/users/{id}`. Сервер применял бы общие правила валидации, а после сохранения форма обновляла бы список с учётом текущего поиска.
- Отправляла бы поисковый запрос после короткой паузы во вводе. При смене фильтра сразу отменяла бы предыдущий запрос и скрывала устаревшие результаты. Это сократило бы число запросов при быстром наборе имени.
- Упростила бы локальный запуск: задала бы значения по умолчанию для адреса, порта и путей к файлам. Тогда после установки зависимостей хватило бы `npm start`, а через переменные окружения можно было бы переопределить настройки.
